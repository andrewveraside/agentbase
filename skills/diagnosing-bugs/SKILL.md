# 诊断 Bug（Diagnosing Bugs）

一套对付难 bug 的纪律。只有在明确理由时才跳过某个阶段。

探索代码库时，若项目有领域词表（GLOSSARY.md），先读以获得相关模块的清晰心智模型；涉及改动区域遵守既有 ADR。

## 脱敏

本技能要求你展示命令、输出与抓取的产物。**先脱敏每个秘密**：用 `<REDACTED>` 替代。针对环境变量构建循环，使凭据留在环境里而非你展示的内容里。抓取的产物可能带鉴权头：只引用承载信号的那些行。

若脱敏后的输出不足以诊断，如实说明并问用户。

## 阶段 1：建立反馈循环

**这就是本技能的核心。** 其它都是机械动作。如果你对这个 bug 有一个**紧致**的 通过/失败 信号（在这个 bug 上会红），你就能找到原因；二分、假设检验、插桩都只是在消耗它。如果没有，盯着代码看再久也救不了你。

在此处投入不成比例的努力。**要激进。要有创意。拒绝放弃。**

### 构造方式（大致按此顺序）

1. **失败测试**，打在能触及 bug 的 seam 上：单元、集成、e2e。
2. **Curl / HTTP 脚本**，打向运行中的 dev server。
3. **CLI 调用**，带 fixture 输入，把 stdout 与已知良好快照 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM/console/network 断言。
5. **重放抓取的 trace。** 把真实网络请求 / payload / 事件日志存盘；在隔离的代码路径里重放。
6. **一次性 harness。** 起一个系统的最小子集（一个服务、mock 掉的依赖），用一次函数调用就能跑通 bug 路径。
7. **属性 / 模糊循环。** 若 bug 是"偶尔输出错"，跑 1000 个随机输入找失败模式。
8. **二分 harness。** 若 bug 出现在两个已知状态（commit、数据集、版本）之间，自动化"在状态 X 启动→检查→重复"，以便 `git bisect run`。
9. **差分循环。** 把同一输入跑过 旧版本 vs 新版本（或两个配置）并 diff 输出。
10. **HITL bash 脚本（最后手段）。** 若必须有人工点击，用 `scripts/hitl-loop.template.sh` 驱动"人"，使循环仍然结构化。抓取的输出回灌给你。

建对循环，bug 就 90% 修好了。

### 收紧循环

把循环当产品打磨。一旦有了**一个**循环，**收紧**它：
- 能更快吗？（缓存 setup、跳过无关初始化、缩小测试范围。）
- 信号能更锐利吗？（断言具体症状，而非"没崩"。）
- 能更确定吗？（钉死时间、给 RNG 播种、隔离文件系统、冻结网络。）

一个 30 秒的 flaky 循环 barely 比没有强；一个 2 秒的确定性循环才是调试超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。把触发器循环 100 次、并行化、加压力、收窄时间窗、注入 sleep。50% 偶发的 bug 可调试；1% 的不行，所以持续抬高复现率直到可调试。

### 真建不出循环时

停下并明确说明。列出你试过的。向用户要：(a) 能复现的环境访问权；(b) 脱敏后的抓取产物（HAR 文件、日志 dump、core dump、带时间戳的录屏）；(c) 添加临时生产插桩的许可。**不要**在没有循环的情况下就跳去假设。

### 完成判据：一个能红的可紧致循环

阶段 1 完成当循环**紧致**且**能红**：你能说出**一条命令**（一个脚本路径、一次测试调用、一次 curl），你**已经至少跑过一次**（展示调用及其输出，已脱敏），且它满足：
- [ ] **能红**：驱动真实的 bug 代码路径，并断言**用户的确切症状**，从而能在这个 bug 上变红、修好后变绿。不是"跑起来不报错"；它必须能**抓住这个具体 bug**。
- [ ] **确定**：每次同样结论（flaky bug：按上文达到钉死的、足够高的复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **可无人值守**：你能不盯着跑；人工只在 `scripts/hitl-loop.template.sh` 里介入。

如果你发现自己还没这条命令就在读代码建理论，**停下：直接跳到假设正是本技能要防止的失败**。没有能红的命令，就别进阶段 2。

## 阶段 2：复现 + 最小化

跑循环。看它随 bug 出现而变红。

确认：
- [ ] 循环产生的失败模式是**用户**描述的那个，不是旁边恰好发生的另一个失败。错 bug = 错修复。
- [ ] 失败跨多次运行可复现（或非确定 bug 达到足够高的复现率可调试）。
- [ ] 你已捕获确切症状（报错信息、错误输出、慢的耗时），以便后续阶段验证修复确实解决了它。

### 最小化

一旦变红，把复现**缩小**到仍会变红的最小场景。一次切掉一项输入、调用方、配置、数据、步骤，每次切完重跑循环，只保留对失败"承重"的东西。

为什么费这劲：最小复现在阶段 3 缩小假设空间（少了的嫌疑对象），并在阶段 5 成为干净的回归测试。

完成当**每个剩余元素都承重**：去掉任何一个都会让循环变绿。

在**复现且最小化**之前不要继续。

## 阶段 3：假设

在测试任何假设前，先生成 **3–5 个排好序的假设**。单一假设生成会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：陈述它做出的预测。

> 格式："若 <X> 是原因，则 <改 Y> 会让 bug 消失 / <改 Z> 会让它更糟。"

若说不出预测，那假设只是感觉：丢弃或 sharpen 它。

**在测试前把排序列表展示给用户。** 他们常有领域知识能瞬间重排（"我们刚在 #3 部署了改动"），或知道哪些已被排除。便宜的检查点，省大时间。别卡在这；若用户不在，按你的排序继续。

## 阶段 4：插桩

每个探针必须映射到阶段 3 的某个具体预测。**一次只改一个变量。**

工具优先级：
1. **调试器 / REPL 检查**（若环境支持）。一个断点胜过十个 log。
2. **定向 log**，打在能区分假设的边界上。
3. 绝不"全量 log 然后 grep"。

**给每个调试 log 加唯一前缀**，如 `[DEBUG-a4f2]`。结尾清理变成一次 grep。未加标签的 log 会留存；加了标签的会死。

**性能分支。** 对性能回归，log 通常不对。改为：先建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），再二分。先测再修。

## 阶段 5：修复 + 回归测试

**先写回归测试，再修**——但仅当存在**正确的 seam**。

正确的 seam 是：测试在调用点处练习**真实的 bug 模式**。若唯一可用的 seam 太浅（单调用方测试，而 bug 需要多个调用方；单元测试无法复现触发 bug 的链），那里的回归测试只会给虚假信心。

**若没有正确的 seam，那本身就是发现。** 记下它。代码库架构在阻止这个 bug 被锁定。为下一阶段标记它。

若有正确的 seam：
1. 把最小化的复现变成该 seam 上的失败测试。
2. 看它失败。若你是通过改代码或 fixture 才逼出红的，和 pristine 副本 `diff` 以证明改动确实落地了，再信任它。
3. 应用修复。
4. 看它通过。
5. 用阶段 1 的反馈循环，对原始（未最小化）场景重跑。

## 阶段 6：清理

宣布完成前必须做：
- [ ] 原始复现不再复现（重跑阶段 1 循环）
- [ ] 回归测试通过（或 seam 缺失已记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 该前缀）
- [ ] 一次性原型已删（或移到明确标记的 debug 位置）
- [ ] 最终证对的假设写进了 commit / PR 信息，让下一个调试者能学到
