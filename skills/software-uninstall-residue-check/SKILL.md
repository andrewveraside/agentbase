# Software uninstall residue check (Windows)

软件"删掉了"通常只删了主程序。残留分五个面，**必须五个都查**，只查文件系统会漏掉最有影响的部分。

| 面 | 查不到时的后果 |
|----|----------------|
| 文件系统 | 白占空间 |
| 注册表 | 「设置→应用」里出现卸载不掉的乱码条目；配置残留导致重装后继承旧状态 |
| 服务 / 启动项 / 计划任务 | **开机变慢、后台常驻** —— 影响最大的一项 |
| 运行中的进程 | 说明文件被占用，删不干净；也说明软件其实还在跑 |
| 回收站 | 用户以为删掉了，其实数据还在（也可能夹带误删的工作文件） |

## 第 0 步：先拿到用户说的"软件名"对应的全部别名

这是最关键的一步，也是最容易做错的一步。同一个产品常有多个名字：

- 同花顺 iFinD → `iFinD` / `iFindEx` / `iFinDLP` / `iFinDWeb` / `iFinDLauncher` / `hexin`（核心）/ `HexinSoft` / `hqplug` / `10jqka` / `hithink`
- 东方财富 → `eastmoney` / `EastMoney` / `Choice`（其金融终端）/ `caifuhao` / `eminfo`

**除非用户明确知道内部名，否则先问他这个软件的主程序和安装目录叫什么**，或者从快捷方式/进程列表反推。
只按产品中文名搜，会漏掉用内部名（hexin / Choice）建目录和写注册表的部分。

## 第 1 步：文件系统 + 回收站 —— 用脚本

```bash
node scripts/residue-scan.js --keys "ifind,hexin,eastmoney,同花顺,东方财富" --roots "C:\,D:\,E:\" --out ./residue.json
```

一次遍历同时产出：
- 每个盘按严格词边界匹配的命中项（含体积、最后改动时间）
- 回收站 `$I` 记录解析出的**原始路径**（让人认出"这是我误删的什么"）

### 短关键词必然误报 —— 硬性规则

**ASCII 关键词 ≤3 字符时，必须要求词边界匹配，否则不要用这个词。**

实测教训：用 `em_` 匹配东方财富，命中了 `Syst**em_**Control`、`WinSxS`、ASUS 日志等，
1,446 个"命中"里 1,380 个是噪声。脚本里 `strictMatch()` 已内置词边界逻辑，不要绕过它加裸关键词。

已知的高频误报源，输出结论前先排除：
- `C:\Windows\WinSxS\`、`Microsoft.NET`、`assembly`、`servicing`、`SoftwareDistribution`
- `AppData\Local\Apps\2.0\`（ClickOnce 缓存）
- `\Temp\`、`\Downloads\`（用户可能只是下过同名文件）
- ASUS / AMD / NVIDIA 厂商日志
- **浏览器的 `IndexedDB\https_<域名>_*`** —— 访问过该网站就有，属正常痕迹，不要列为残留
- **云盘里的合同/文档**（例如《XX 数据服务费合同.pdf》）—— 是业务资料，误报重灾区

## 第 2 步：注册表 —— 先导出清单，再筛选

### 本环境的关键约束：`reg.exe` / `sc.exe` / `schtasks.exe` 被黑名单拦截

**拦截时不会把错误写到 stdout**，脚本只看到空输出，于是会把"没查成"当成"查了没有"。
第一次排查时我就踩了这个坑：所有键都被误报为"存在"，幸好发现输出为空而作废重来。

因此**不要**用 `execFileSync('reg', ['query', ...])` 这条路。改为：
用 PowerShell 工具把清单整体导出到文件，再用 Node 读文件筛选（Node 的 UTF-8 处理可靠）。

需要导出的六张清单：
1. `HKCU` / `HKLM` / `HKLM\WOW6432Node` 三个 `...\CurrentVersion\Uninstall` 的 `DisplayName`
2. 四组 `Run` / `RunOnce` 启动项
3. `HKCU\Software`、`HKLM\SOFTWARE`、`HKLM\SOFTWARE\WOW6432Node` 的一级键名
4. `Get-Service` 的 Name + DisplayName
5. `Get-ScheduledTask` 的路径
6. `Get-Process` 的 ProcessName + Path

注意：项目含中文关键词时，**不要把带中文的脚本写成 .ps1 文件**（编码会损坏），用内联命令；
导出统一 `-Encoding UTF8`，并且**清单里只放结构名、筛选在 Node 侧做**。

### 乱码的卸载登记项不能当噪声丢掉

实测有一条 `...\Uninstall\同花顺_is1`，其 `DisplayName` 在控制台显示为 `ͬ��˳`。
原因是写入时 GBK、读取时按其他编码解，**落盘核对才确认实际名称是「同花顺」**。
这类条目恰恰是影响最大的残留（「设置→应用」里一条乱码、点了卸载会失败的项）。
筛选时要把含替换字符（`\uFFFD`）的行单独列出来人工确认，不要过滤掉。

## 第 3 步：回收站 —— 清空前必须逐项还原

回收站常有两类东西：
- 用户删掉的主程序本体（这些"残留"其实在回收站里，不在盘上）
- **夹带进来的、用户没打算删的工作文件**

解析 `$I` 记录即可还原原始路径。格式（小端）：

```
偏移 0  : 8 字节 头（版本信息）
偏移 8  : 8 字节 原始大小 BigUInt64LE
偏移 16 : 8 字节 删除时间（FILETIME）
偏移 24 : 剩余字节 = 原始路径，UTF-16LE，以 \0 结尾
```

`$R` 同名文件是内容本体。脚本已实现，直接看输出。

**注意**：`$RECYCLE.BIN\<其他 SID>`（如 `S-1-5-18` 即 SYSTEM）会 `EPERM`，
`readdirSync` 必须包 try/catch，跳过即可，属正常。

## 第 4 步：判断"是否还算残留"也要给依据

对每个命中项至少给一条依据，不要只列路径：

| 依据类型 | 例子 |
|----------|------|
| 无卸载程序 | 目录里搜 `uninst*` / `卸载` 无结果 → 说明当初是直接删文件夹，注册表必然没清 |
| 自更新器残留 | 目录里留着 `DeleteFolder.xml` / `checksum_file` / `package.json` → 是更新器的工作文件 |
| 版本号比对 | 读 `package.json` / `manifest.json` 取版本，与当前在用的版本区分新旧 |
| 清单集合差集 | Steam 用 `appmanifest_*.acf` 建已装集合，与 `common\` 实际目录做差 |
| 进程/服务为 0 | 说明没有后台常驻，处理优先级可降为"洁癖级"而非"救火级" |

**结论要先说影响等级**（会不会影响开机/后台/功能），再说体积。用户真正在意的是前者。

## 输出与安全

- 报告分级：`需要处理` / `需要确认（可能含用户数据）` / `不要动（名字像但不是残留）`
- **回收站里有用户数据时，放在报告最前面**，并要求用户先确认再清空 —— 这是唯一不可逆的动作
- 全程只读：扫描阶段不改任何文件。清理动作必须**先列确切清单、经用户确认**，注册表操作前先导出备份
- `HKCU\Software` 下的键当前用户权限即可删；`HKLM` 下的需要管理员，不要代为提权，交付命令让用户自己跑
