# xlsx 外科式读写（不依赖编辑器后端）

## 何时用

- `tencent-local-office-edit` 的 `edsdk.py` 报 `连接失败 / WinError 10061`（探测 39099–39108 全闭）。
- `sheet-agent` 子代理报告「写入成功但回读为空」——这通常是它读写到了两个不同的编辑器实例，**改动从未落盘**。
- 需要「只动这几个单元格，其余字节级不变」的确定性修改。

**先做的第一件事**：用 `present_files` 之外的途径确认磁盘现状，不要相信任何编辑器实例的内存状态。

## 环境要点（Windows）

- `python3` 不在 PATH，用 `C:\Users\23171\.workbuddy\binaries\python\versions\3.13.12\python.exe`
- 该 bash 环境**没有** `mkdir` / `dirname` / `head` / `tail` / `find`，需要时改用 PowerShell
- **不必装 openpyxl**：zipfile + ElementTree 足够，而且不会破坏文件（openpyxl 往返会丢掉公式的缓存值）

## 读：拿到真实内容

`.xlsx` 就是个 zip。关键路径：

| 内容 | 路径 |
|---|---|
| 表名 → part 映射 | `xl/workbook.xml`（`<sheet name= r:id=>`）+ `xl/_rels/workbook.xml.rels` |
| 单元格数据 | `xl/worksheets/sheetN.xml` |
| 共享字符串 | `xl/sharedStrings.xml` |

要点：

- **表在 zip 里的 part 名与表顺序无关**，必须走 `workbook.xml.rels` 解析，不能假设 `sheet1.xml` = 第一张表。
- **公式单元格的值**在 `<c t="str"><v>…</v></c>` 的 `v` 里，就是上次 Excel 保存时的缓存结果——**可以直接读出来用**（本次就是靠它读到了 `C 识别项目` 这个拼接键）。
- 取值优先级：`t="s"` → 查 sharedStrings；`t="inlineStr"` → 取 `<is><t>`；否则取 `<v>`。
- 合并单元格：`<mergeCells>` 里只有区间，**值只存在左上角那个格子**，其余同区间的格子是空的。要判断某行属于哪个"合同块"，必须把区间展开成行集合。
- 结构声明：`<dataValidations>`、`<sheetProtection>`、`<sheetViews><pane>`、`<hyperlinks>`、`<conditionalFormatting>`。**没有**这些节点就是真的没有——这是编辑器通道查不到的。

## 写：外科式替换（推荐）

思路：**只改 `xl/worksheets/sheetN.xml` 里的目标 `<c>` 节点，其他 part 原样搬回去。**

```python
# 1) 备份
shutil.copy2(TGT, BAK)

# 2) 全部读进内存
zin = zipfile.ZipFile(TGT)
parts = {n: zin.read(n) for n in zin.namelist()}

# 3) 定位行、插入/替换单元格（字符串级操作，不用 ET 重序列化整表）
xml = parts[part].decode('utf-8')
# 行块：<row r="22" ...> ... </row>
# 插入位置：该行第一个列号 > J 的 <c> 之前；列号比较要把字母转成数字
# 已存在 <c r="J22" s="46"/> 时，就地替换并保留 s="..." 样式

# 4) 原样写回（条目名列表保持不变）
zout = zipfile.ZipFile(TGT, 'w', zipfile.ZIP_DEFLATED)
for n in zin.namelist():
    zout.writestr(n, parts[n])
```

写值用 `t="inlineStr"`：`<c r="J22" s="46" t="inlineStr"><is><t>值</t></is></c>`

- **用 inlineStr 而不是往 sharedStrings 追加**——不用动 `sharedStrings.xml`，少一个污染点。
- **必须保留原有的 `s="…"` 样式索引**，否则格式会掉。
- 注意 `spans="1:60"` 之类属性不用改。
- 文件里通常**没有 `calcChain.xml`**（本次就没有），不用维护。

## 校验：写完必须自己验（不可省）

对着备份做差集，逐项确认：

1. **XML 可解析**：每张表 `ET.fromstring` 不报错。
2. **目标值正确**：写入的值与计划逐格比对，不一致数 = 0。
3. **其他表零改动**：非目标表的 XML **字节完全一致**（`bytes` 直接相等）。
4. **目标表其他列零改动**：排除目标列后，单元格字典完全相等。
5. **结构未变**：合并单元格集合相等、新增/丢失 = 0。
6. **无重复单元格**：每行 `<c r=...>` 无同列重复（插入顺序错了会出现）。
7. **zip 条目名列表一致**。

## ⚠️ 并发风险

编辑器实例若持有**过期副本**且用户点了保存，会覆盖你的直接写入。
直接改盘后，**明确告知用户关掉再重新打开文件**，不要从旧实例保存。

## 编辑器通道可用时：优先走它（本文件 2026-09-22 补）

`edsdk.py` 能连通时，**先走编辑器通道**，比直接改盘更安全（有 revision、实时可见）。流程：

```bash
edsdk.py call get_pool_status                       # 找实例；file_id 可能是 UUID，也可能是路径字符串
edsdk.py call open_file --json '{"file_path":"...","file_type":"sheet"}'   # 池里没有就打开
edsdk.py schema <工具名>                             # 硬规矩：调用前必查 schema
edsdk.py call sheet_set_range_value --json-file payload.json
edsdk.py call save_file file_id=<id>
```

**踩过的坑**：

- 🔴 **最坑的一条：编辑器内存 ≠ 磁盘。写操作后必须先 `save_file`，再读磁盘校验。**
  2026-09-23 实测：用 `sheet_delete_dimension` 删了 25 段共 96 行，**没保存**就去 zipfile 读磁盘做诊断，
  读到的是未保存的旧状态（行数还是删前），于是误判成"删错位置、把尾部截断了"，
  白排查一轮（临时副本实测才证明删除语义其实完全正确）。
  **绝不能用磁盘读去推断编辑器的内存状态。**
- 🔴🔴 **同路径可能有多个实例，`save_file` 会把「你指定的那个实例」整份写盘 —— 指错了就是回退磁盘！**
  实际事故（2026-09-23）：`get_pool_status` 里同时存在
  `E:\...\x.xlsx`、`E:////...\x.xlsx`（斜杠翻倍变体）、以及若干 `file_path` 为空的游离实例。
  我对一个**游离的旧副本**调了 `save_file`，把用户手工填好的 5 个单元格**覆盖回了空**。
  **正确做法**：写入/保存前先 `get_pool_status`，只选
  `file_path` 非空 **且** `last_saved_ms != -1` 的那一条，用它的 `file_id`；
  凡 `file_path` 为空、`last_saved_ms == -1` 的实例一律视为游离旧副本，**不要写、更不要 save**。
  写完 `save_file` 后，**再用 zipfile 读磁盘复核一次关键单元格**，确认没有把别人的改动冲掉。
- 删行/插行的 `index` 是 **0-based 起始行**，`count` 为行数；`index=a-1, count=n` 删掉的正是第 a..a+n-1 行（实测正确）。
  多段增删**自下而上**（按起始行降序）处理，可保证每段的 index 在处理时仍然有效。
- `workbook is not open` → 实例已失效（后端重启过）。重新 `open_file` 或再 `present_files`，**不要**在旧 file_id 上重试。
- `pool_size: 0` 时同样先 `open_file`，**并回读一次核对内容与磁盘一致**才动笔。
- `open_file` 返回的 file_id 有时是**路径字符串**且斜杠被翻倍（`E://a//b//c.xlsx`）。它能正常读写与保存，不必强行纠正。
- 写值格式：`{"row":<0-based>,"col":<0-based>,"value_type":"NUMBER|STRING","number_value"|"string_value":...}`。
  中文全角标点（如 `（原合同终止）`）用 `--json-file` 传，别用 shell 内联，避免编码损坏。
- **`sheet_get_cell_data` 的 `return_csv=true` 返回的是「格式化后」的文本**：日期显示成 `2025/8/1`、
  金额带千分位 `22,300,618.65`。**回读校验时必须先按格式反解析**（`yyyy/m/d` → 日期序列值、去掉逗号 → float），
  直接跟原始值比对会满屏假报错。
- **日期列务必先查数字格式**。某表 K 列第 10 行以下 432 格是「常规」格式，写序列值会显示成
  `46023` 而不是日期。修法：`sheet_set_cell_style` 传 `"format":{"number_format_pattern":"yyyy/m/d"}`。
  日期一律**写序列值（NUMBER）**而非文本——文本日期不能参与筛选/排序、也不能与台账比对。
- 加列：`sheet_insert_dimension {dimension_type:"col", index:<0-based>, count:1, direction:"after"}`
  —— `direction="after"` 继承左列属性；**列索引越界会直接报 `end_col >= col_count`**，必须先加列再写。
- 新建子表用 `sheet_add_sheet {name: ...}`（参数名是 `name`，不是 `sheet_name`），
  新表默认只有 200 行 —— 内容更多要先 `sheet_insert_dimension` 扩行。
- `save_file` 有时要求显式 `file_path`（报 `no original path registered`），传上就好。
- 大批量写值一次调用即可（实测 1536 格一次成功）；逐格调用纯属浪费。

## 配套纪律：匹配类任务先用「已知真值」验策略

跨表匹配（把 A 表的编号填到 B 表）不要直接按感觉跑规则。做法：

1. 先取一个**已知真值的子集**（本次用「上一轮已确认的 39 行 + 本轮可严格推导的 72 行」= 111 行）。
2. 对每个候选匹配策略（不同的字段组合）在这 111 行上跑，统计**唯一定位数 / 命中数 / 精确率**。
3. **精确率不达标就不填**。本次第一轮各策略精确率 12.5%–68%，全部否掉——宁可报告「这个数据源做不到」，也不要给出看似完成实则一半错的结果。
4. 报告里必须写清：用了哪些字段、判定"唯一"的标准、精确率是怎么测出来的、失败样例长什么样。

**两个可复用的提纯手法**（本次把精确率从 50% 提到 90.9%，靠的就是这两条）：

- **先看真值本身的取値分布，找出「合法値域」**。本次发现工作台的编号第三段起初只有 `WZ`/`WX`
  两种（47+26，无一例外），后来随新场景扩到 `WZ`/`WX`/`WY`/`ZT` 四种（共 395 个编号），
  而数据源里还有 `QQ`/`ZF`/`ZZ`/`ZC`/`ZX`/`ZJ`/`LZ`… 十余种段位。
  其中 **`QQ` 是"零星杂项"段**（消杀、垃圾清运、房屋/车位租赁、用电协议、物资与设备转让、车辆维修…，
  全表 890 条），**从不出现在主合同收入类行**——必须列入排除名单。
  按这个值域过滤候选，一步砍掉大部分错配。**这类"编码本身携带类型信息"的规律极值钱，一定要先查。**
  ⚠️ **但値域会随业务扩张**：发现新段位时先看它的合同名分布，再决定是"扩白名单"还是"加黑名单"，
  不要默认它一定是错的。
- **分析错配的「模式」而不是数量**。本次 6 处不一致全部是同一种模式——数据源里存在**更新版本的
  同一份合同**（后续年度的续签件）。识别出这是"找到了更优答案"而非"匹配错了"，结论就完全相反。

**验收时要区分「错」与「不同」**：真值往往是"上一轮的口径"，不一定是"本轮正确的答案"。
逐条看错配明细并归类，比只看精确率数字靠谱。

## 配套纪律：批量生成「原因说明」时，统计口径必须与判定口径一致

给未匹配项写原因备注（"同 XXX 有 N 条记录，**均不覆盖**某条件"）时，**极易犯一个错**：
N 是**按 A 口径**（如"业务单元名命中"）数的，而"是否满足条件"却施加在**B 口径**（如"同报表主体"）
的子集上——两个集合不是同一个，于是出现"**明明有符合条件的记录，却写'均不覆盖'**"。
本次因此让 8 行（约占当时空白行的 18%）备注失实，把用户引向了错误方向。

**规则**：

1. 一句话里的**每个数字与它修饰的集合必须是同一个**。要写"均不覆盖"，就得用**同一集合**去算覆盖。
2. 生成后**回读复算**：把该句的集合重新算一遍，逐行验证断言（本次用 `assert` 式复核才发现）。
3. 结论取决于口径时，**把口径写进备注**（"与本行报表主体一致、覆盖当年的 N 条"），
   而不是给一个模棱两可的总数。
4. 修正后要**全局搜旧措辞残留**（本次搜「均不覆盖 2026」），确认只在真实成立的行上保留。

## 配套纪律：交付前跑一遍「全表终检清单」（可复用）

填完之后不要只抽检几行。写一个脚本把下列断言全部跑一遍，输出一张通过/不通过的表——
本项目（441 行收入查验底稿 × 17944 行合同台账）就是这样在终检里又揪出 4 行填错的。

**结构层**：行数/列数、公式列非空数、最右列、合并单元格数、工作表清单、旁表逐格与备份比对。

**取值层**（对每个已填的「外键」值）：

1. **可溯源**：该值能否在参照表里找到（本次：编号在台账 N 列存在）→ 应为 0 缺失。
2. **有效性**：该值指向的记录是否满足业务条件（本次：合同期覆盖当年、状态非作废/终止）。
3. **配套列一致**：一同填入的派生列是否等于参照记录的对应字段（本次：K/L/M = 台账 D/E/G）。
4. **值域**：编码本身携带的类型位是否落在合法集合内（本次：编号第三段 WZ/WX/WY/ZT，
   出现 QQ/ZF/ZZ 等即为可疑）——**能一次筛出大量错配**。
5. **行唯一键**：把"应该是唯一的键"（本次 `B+F+E+I` 四段拼接）分组，查是否出现两个不同的外键值。
   ⚠️ **前提是键要完整**：少一个维度（本次少 F）会把 61 组正常的多费项行误报成冲突，
   跑出来先怀疑自己的键，再怀疑数据。
6. **主键吻合度分层**：把"逐字一致 / 同根（前缀容忍层级差异）/ 不符"分别计数。
   **"不符"的那一小撮必须逐行给出解释并写进备注**，否则就是埋雷。
7. **空缺项**：所有未填的都要有原因说明；`assert 无备注 == 0`。
8. **外键被多行共用**：统计并**接受**它（统筹标段、一合同多费项行的正常现象），
   但要在备注里写明"一份合同覆盖多单元、派生列取整份口径、不拆分"。
9. **与备份的差异必须收敛到预期列**：`diff` 里出现任何"非目标列"都要立刻查。
10. **用户手工改过的单元格**：记下行号，终检时单独确认完好（本次行 3–9、18–21）。
