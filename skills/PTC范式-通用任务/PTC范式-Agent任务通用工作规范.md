# PTC 范式 · Agent 任务通用工作规范

> **版本** v2.0（通用化修订）｜ **日期** 2026-10-17 ｜ **性质** 通用方法规范，不绑定任何具体客户、项目或任务类型
> **适用判断**：一切**多步骤、大数据量、多工具/多源**的任务——只要中间结果体量明显大于最终交付物，就适用。表格核对只是其中最典型的一类，不是全部。

---

## 0. 一页结论（先看这里）

**核心原则一句话：让数据在代码里跑完，只把结论带回上下文。**

三条规则：

1. **中间结果不进上下文** —— 大体量中间结果（筛选行、检索命中、过程稿、原始返回）一律落盘（文件/临时存储），模型上下文里只放汇总、差异和定位信息。
2. **一次推理完成编排** —— 能写进一个脚本/一次规划的循环、条件、多源关联，不要拆成"读一批 → 回传一批 → 再读一批"的多轮往返。
3. **错误是值，不是轮次** —— 可预期失败在工具/脚本内处理，把失败统计成数字带回来；只有需要人判断的意外才中断回传。

一张决策卡（详见第 4 节）：

| 数据的命运 | 处理方式 |
|---|---|
| 被工具/脚本消费、不再被逐条看 | 全程不进上下文 |
| 需要人或模型逐条判断 | 只回传这一部分，且做字段投影/裁剪 |
| 最终交付结论 | 回传，含数字和定位信息（行号/路径） |

**省多少取决于场景**：数据密集型任务省得多（社区实测 85–98%），普通多步任务约 37%，轻量任务几乎不省。看到任何"节省 N%"的说法，先问：什么场景、什么基线、谁测的（详见 6.2）。

## 1. 这套规范要解决什么问题

### 1.1 症状（通用，不止表格）

- 整份大文件/整表读回上下文，实际有用的只有其中一小部分；
- 多源任务（多文件、多工具、多知识库）按"读一个、对一批、再读一个"逐轮往返，每轮中间结果全量常驻；
- 上下文被中间数据挤占后，注意力被稀释，关键证据反而更容易看错、关键指令更容易被忽略。

### 1.2 根因

传统 tool call loop 的结构性缺陷：**每次工具调用的结果整体进入上下文**，3 个工具 = 3 次推理往返 + 3 份全量结果常驻。数据量越大，浪费与上下文膨胀越严重。这是 agent 架构的共性问题，与任务类型无关。

```
传统 loop：  模型 → 工具1（全量结果进上下文）→ 模型 → 工具2（全量结果进上下文）→ 模型 → 答案
PTC 范式：   模型 → 写一次脚本/一次规划 → 代码内循环消费数据 → 只把汇总/差异带回 → 模型 → 答案
```

### 1.3 分类覆盖

本规范按任务类型给出落地规则（第 3 节）：**大表格核对、代码项目、资料检索、文档生成、多工具链、文件批处理**。未列出的新类型，用第 4 节决策卡自行判断。

## 2. PTC 范式的三条核心原则

> 来源：dsh-ops 的 PTC 组件设计（`docs/native-ptc.md`）与 Anthropic Programmatic Tool Calling（2026-02-18 GA）。两者同范式，以下为提炼后适用于本环境（WorkBuddy + 本地 Python + 各类 MCP/连接器）的版本。

### 原则一：中间结果不进上下文

大结果（超过一屏的条目级数据）不直接回传，而是：

1. 写入明确约定的临时目录（如 `_work/` 或 scratch 目录）；
2. 回传时只给**统计数字 + 定位信息**（多少条、涉及哪些行号/文件/ID、在哪个路径）；
3. 需要看具体内容时，用**分页 + 字段投影**按需读取（只取需要的字段、只取前 N 条）。

类比：不要把整摞原始凭证搬上桌面，只把"有问题的 3 张"和"问题摘要"放上来。

### 原则二：一次推理完成编排

一个脚本/一次规划内完成循环、条件分支、多源关联：

- 多轮才能说完的处理逻辑（分组、分摊、匹配、汇总），写进一个脚本一次跑完；
- 只 `print`/回传摘要（计数、合计、清单），不回传全量过程数据。

### 原则三：错误是值，不是轮次

- 可预期失败（缺列、类型不符、文件打不开、某工具超时）在脚本/编排层捕获，累计成"失败 N 项，类型分布：{...}"一并带回；
- 只有**需要人判断的意外**（规则冲突、口径不明）才中断回传，且带回时附上已排除的可能和具体定位。

## 3. 分项目类型落地规则

### 3.1 大表格核对（合同查验、费用核对、抽凭、账表比对）

做什么：

- 探查先行：脚本输出行列数、列名、关键列唯一值计数、前 2 行样例，不整表读回；
- 匹配逻辑（键定义、优先级、交叉过滤）写进脚本一次跑完，结果分 `matched`/`unmatched`/`conflict` 三类落盘，回传三类计数 + 行号清单 + 前 5 条样本；
- 差异按类型聚合（金额不符/错配/无依据/口径待定），每类给计数 + 代表行；
- 计算全部完成后一次性写回**工作副本**，写回后回读抽查已知值。

不做什么：不逐行复述匹配过程；不把全量差异铺进上下文；不强行匹配未命中项。

### 3.2 代码项目（读大文件、跨文件检索、批量修改）

做什么：

- 用检索工具定位（grep/glob），只读命中行及上下文，不整文件读入；
- 跨文件分析（调用链、依赖、影响面）用脚本聚合，回传结构摘要 + 文件路径清单；
- 批量修改前先出 **dry-run 报告**（将改哪些文件、各改几处），确认后执行；
- 长输出（测试日志、构建日志）只回传尾部失败段 + 统计。

不做什么：不因"顺便看看"读入与任务无关的大文件；不在未确认影响面前景下批量改写。

### 3.3 资料检索（知识库、ima、联网搜索、法规查询）

做什么：

- 先定位后取全文：搜索 → 拿候选清单 → 只对相关条目取正文/摘要；
- 大批命中时，脚本/分页处理，回传统计 + 最相关 N 条的要点；
- 法规/税率/口径类问题，以权威源原文片段作答并注明出处，不凭记忆转述。

不做什么：不把全部命中结果一次性铺进上下文；不跨库复用未在本轮验证的 ID/结论。

### 3.4 文档生成（长报告、规范、手册）

做什么：

- 先定大纲（结构即契约），分模块写作，中间稿落盘；
- 每个模块只回传要点/字数/结构变化，不全文回传；
- 终稿合并后做一致性检查（术语、编号、交叉引用）再交付。

不做什么：不在上下文里反复重写已定稿的长章节；不做无大纲的长文直写。

### 3.5 多工具链任务（多 MCP/多连接器编排）

做什么：

- 梳理工具依赖，能合并的调用合并（一次拿齐后续都用的数据）；
- 前一工具的产物作为后一工具的输入时，走"落盘/传引用"，不回传全量；
- 每个工具的回传都做裁剪：只留后续决策需要的字段。

不做什么：不为拿一个字段触发一次全量拉取；不在工具间用上下文当数据管道（那是第 2 节原则一说的"数据管道"反模式）。

### 3.6 文件批处理（整理、重命名、迁移、清理）

做什么：

- **第一阶段只读扫描**：输出清单（路径、大小、日期、命中原因），不做任何改动；
- 按用户确认的规则生成**执行计划预览**（将做什么、影响哪些文件），确认后分批执行；
- 每批执行后验证（计数、抽验），失败即停。

不做什么：不跳过扫描直接动手；不做无预览的批量破坏性操作（详见第 5 节红线）。

## 4. 决策卡：什么进上下文，什么进脚本

| 数据/产物特征 | 判断 | 处理 |
|---|---|---|
| 体量大、只消费不逐条看 | 工具食材 | 全程不进上下文 |
| 体量大、需逐条判断 | 判断对象 | 字段投影后分页回传 |
| 体量小、是关键证据 | 证据 | 整段回传（含定位：行号/路径/ID） |
| 统计数字、清单、路径 | 导航信息 | 回传 |
| 过程数据、试错记录、原始返回 | 过程废料 | 落盘，不主动回传 |
| 用户已填/已确认的值 | 最高权限口径 | 只读不改，作为基准 |

回传前的三问（每次 print/回传前过一遍）：

1. 这个内容，下一步决策真的要用吗？
2. 能不能用更少字段、更少条目表达同一信息？
3. 回传的内容，用户复核时看得过来吗？

## 5. 与既有工作原则的衔接（不可突破的边界）

PTC 优化的是**数据通道效率**，以下原则优先级更高，任何脚本化/自动化都不得突破：

### 5.1 原始数据保护

所有写操作发生在工作副本或用户明确授权的目标上；原始文件、他人数据只读。临时中间结果目录与交付物分开放置，任务结束说明去向。

### 5.2 用户口径优先

用户手填值、已确认的规则和决定是最终口径。脚本/工具对它们只读；发现口径与计算值不一致时，**报告差异，不改写**。

### 5.3 准确性优先于覆盖率

匹配类任务：仅写入高度确认的结果，宁缺毋滥，unmatched 就留在 unmatched。生成类任务：存疑处显式标注"待确认"，不虚构。

### 5.4 差异优先披露

差异如实呈现、按类型聚合。不为美观、不为"压低条数"而合并或隐藏差异。

### 5.5 验证先行

任何新规则/新假设：先用具体样本验证（拿 1-2 个真实数据点手算比对），通过再批量应用。验证是编排的前置步，不构成额外轮次。

## 6. 两个必须内化的观念

### 6.1 "减少循环思考"是误读

PTC 省的是**工具往返对上下文的占用**（中间结果不进上下文、一次推理完成编排），不是让模型"少思考"。判断质量取决于模型和输入信息的信噪比——本规范正是通过提高信噪比来保护判断质量。

### 6.2 对"节省 N%"保持条件反射式怀疑

同一范式下，官方口径 37%、社区口径 85–98%、某项目 README 自称 97%（作者自注：仅单场景自测，不可泛化）。**数字离开场景就没有意义。** 采用任何优化手段前，用自己的任务实测一轮基线，再决定是否值得固化。

---

## 7. 每轮任务自检清单

任务收尾前逐条过：

- [ ] 原始文件/他人数据未被改动；
- [ ] 所有写回都发生在工作副本或授权目标；
- [ ] 中间结果已落盘且路径已说明；
- [ ] 回传的每个数字都可由脚本/工具重算复现，不手抄；
- [ ] 未匹配/冲突/失败项全部列明，无强行匹配、无静默跳过；
- [ ] 差异按类型聚合，代表项可定位；
- [ ] 用户口径列未被改动；
- [ ] 若引入新规则：已用具体样本验证过；
- [ ] 本轮上下文里没有"本可留在盘上"的大块数据；
- [ ] 批量/破坏性操作前有过只读扫描和计划预览。
