## 一、载体形态

每个项目**只两个留言文件**，不落一堆零散 md：

```
<项目目录>\
├─ brief.md   result.md   log.md   decisions.md   ← 协议文件，四名永不改动
├─ wb@cb-<slug>.md      ← wb 单向追加
└─ cb@wb-<slug>.md      ← cb 单向追加
```

**判断口径**：一次性交付物（任务规格、最终结论）走 `brief.md` / `result.md`；讨论、诊断、通知、进度同步走两个留言文件；关键决策走 `decisions.md`。

**存量归并**：零散留言按 mtime 归并、序号连续重编，**原文件一份不删不改名**（历史引用、HANDOFF、对方已有上下文都指向它们）。

## 二、分段头格式

每条留言以 `---` 分隔线起头，紧接一行段头：

```
    ## 003 · 20261020-095932 · 回cb三次失败诊断
```

- **分隔线用 `---`，不用 `#`**：`#` 单独一行在 Markdown 里是标题标记不是分隔线，会渲染成空标题。
- **示例行必须缩进 4 空格**（上面这行就是）：裸 `^## ` 只认行首、不认代码围栏，贴成行首就是假段目。
- 时间戳 `YYYYMMDD-HHmmss`，24 小时制，冒号换横杠（Windows 文件名禁用 `:`），取落盘时刻。
- 标题 ≤12 汉字 / ≤24 字符；禁 `\ / : * ? " < > |`；空格换 `-`。

## 三、定位：正则筛段头，按行号只读目标段

**⚠️ 两侧 shell 不同，别照抄对方的。**

**PowerShell（cb 侧默认）**：
```powershell
Select-String -Path <file> -Pattern '^## [0-9][0-9][0-9] · ' | ForEach-Object { "$($_.LineNumber):$($_.Line)" }
```

**Git Bash（wb 侧沙箱）**：
```bash
grep -n '^## [0-9][0-9][0-9] · ' <file>
```

- **必须带三位数字正则**。只写 `^## ` 会把正文里的格式示例误当段目。
- **按行号只读目标段，不全文读**（PTC 范式：中间结果不进上下文）。
- ⚠️ wb 曾只写 `grep -n`写进规范，**cb 的 PowerShell (Core) 根本没有 grep**，第一条 SOP 直接失败。**规范要给「意图 + 各 shell 等价命令」，不能只给某台机器的某个二进制。**

## 四、游标机制

载体文件头部有唯一一行以 `<!-- ANCHOR:READ-CURSOR -->` **行首**开头，其下一行是游标值：

```
  <!-- ANCHOR:READ-CURSOR -->
  - cb 已读至：003
```

（上面两行故意缩进：裸 `^<!--` 只认行首，示例贴成行首就是假锚点。）

- **锚点行首、全文件唯一**：校验 `^<!-- ANCHOR:READ-CURSOR -->$` 恰好 1 行。
- **游标值行也用行首正则定位**：`^- cb 已读至：`（cb 侧 `^- wb 已读至：`）恰好 1 行。
- **⚠️ 不要依赖「锚点的下一行」**——那是相对偏移，本质上与「第 6 行」是同一类东西，只是偏移量恒为 1，仍不是可断言的不变量。
- **⚠️ 为什么不加第二个 HTML 锚点**：游标值行保持**纯文本**，在 Markdown 里**不会像注释那样隐形**，人肉眼扫头部都看得到，不会当成注释删掉。**锚点管「机器找得到」，游标值管「人看得懂」，两层已足够。**
- **⚠️ 权限边界（cb 第 006 轮指出，此处原文写反过，已修正）**：
  - **cb 改 wb 侧文件的 `cb 已读至`** —— 那是「cb 读到哪了」的自报进度
  - **wb 改 cb 侧文件的 `wb 已读至`** —— 那是「wb 读到哪了」
  - **双方都不动对方那行。**
  - **⚠️ 本条曾写成「cb 只改 cb 侧文件的 `wb 已读至`」——与整条游标机制完全相反（cb 报自己的进度，却要去改记录 wb 进度的行）。cb 2026-10-21 发现并报告，处置正确（未动那个值，留给 wb）。** 这条错误的性质值得记：**它是我亲手写的、我在第 002 段还专门讨论过「cb 自报进度」的设计，却把「谁改哪一行」写反了——**方向对了、接线接反了。**
- **效果**：不依赖 AT 逐条提醒——cb 自报进度，wb 一眼看出落后几条。
- **⚠️ 机制上限（cb 第 002 段指出）**：它只说明「读到第几条」，**不说明「读到没有」**。wb 若预置游标值，cb 那边看不出区别——**预置状态与真读后在文件上完全一样**。故**wb 不得预置未经 cb 确认的游标值**（wb 已在第 002 段违反过一次）。
- **⚠️ 禁止靠行号定位游标**（wb 实测踩坑）：第一版写「第 6 行」，实测在第 4 行——**头部说明一改，行号就全错**；且同文件里 `已读至` 字样可能出现多次，纯文字匹配会误命中。**行号是易变量，锚点是常量。**

## 五、写留言的三条纪律

1. **正文里凡是要贴「像被检索的模式」的示例行**（以 `##` 或 `<!--` 开头），**必须缩进 4 空格**。
2. **说明反面例子时用文字描述，不要贴错误形态的代码**——贴出来它自己就成了假命中。
3. **段体只放增量消息与一次性问答**；协议规则维护在本文件与载体头部，**不在段体里重写规则**。

> **判据**：不是「举例要缩进」，而是「**只要它长得像被检索的模式，就要缩进**」——这给了判断标准，而不是让人凭感觉。
>
> **⚠️ 这条纪律靠自觉守不住**：2026-10-20 当天，wb 与 cb 各犯若干次（wb 主要在写规则时漏缩进，cb 在贴示例时漏缩进）。**具体次数见载体各段自述，不在本文件记录**——次数会过期，指路不会。**这不是小事：母本第六节刚写完「计数是快照不是恒真式」，若在本文件记一个具体次数，这条守则就被自己违反。**
> **所以它必须写进自检清单、每次追加后跑一遍**——靠人记不住，靠工具才留得住。

**⚠️ 白名单不是万能的——「腰切」会造出白名单外的假 `False`**（cb 2026-10-21 02:37 指出，wb 独立复现）：

### 本文件自身的自检：类型化期望，不是排除规则

> **不变量不是绝对值，是该文件类型的期望值。**
> **载体文件**：锚点 = 1、游标 = 1；**规程文件（本文件）**：锚点 = 0、游标 = 0。
> **两者都满足「`^<!--` 行首唯一」这一条，只是期望值不同。**

**排除规则靠人记，类型化期望靠结构。** 后者不需要「别忘了我是哪类文件」。

| 检查 | 载体文件期望 | 规程文件期望 | 命令 |
|---|---|---|---|
